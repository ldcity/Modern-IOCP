# `modern-iocp` 를 무엇으로, 어떤 스택으로 다시 쓸 것인가

- 결정일: 2026-08-29
- 결정자: 사용자 (Claude 는 후보 정리와 근거 제시만)
- 근거 문서: `D:\GameProjects\Docs\PORTFOLIO_AUDIT.md` §3.3

## 문제

2024 IOCP 포트폴리오 5종은 구현량이 적지 않다. 세션 수명, IO 참조 카운트, 패킷 풀,
lock-free 자료구조, 성능 카운터, crash dump, DB/Redis, 서버 간 프로토콜을 직접 구현했다.
그런데 감사 판정은 "구현량은 많은데 커밋 역사와 README 가 얇아, 면접관은 무엇을 직접
설계했고 어떤 버그를 해결했는지 알기 어렵다" 였다. 테스트·CI·고정된 의존성 버전·재현
가능한 실행 경로가 전부 없다.

여기에 확정된 제약 셋이 붙는다 (2026-08-29).

1. **레거시 IOCP 코어는 실무 경험이 없던 시절의 구현이다.** "IOCP 를 써 봤다" 고 말하기에는
   추상화 수준이 너무 낮다. 손질이 아니라 **전면 재개편과 재학습**이 목적이다.
2. **현재 실무 스택은 Boost.Asio 인데 공개 git 기록에 Asio 사용 이력이 없다.**
   실무 스택을 증명할 자산이 없는 상태다.
3. 🔴 **이 저장소의 코드는 소유자가 직접 설계·구현한다.** 소유자가 설명할 수 없는 코드는
   포트폴리오로서 값을 하지 못한다는 것이 이 저장소를 별도로 둔 전제다. AI 의 역할 경계를
   문서로 고정하고 지키는 것 자체가 산출물의 일부다.

## 후보

### 범위

1. **IOCP Reliability Lab** — 신규 단일 저장소. MMOFighter 의 IOCP 네트워크 코어 +
   LoginServer 의 인증/Redis + Monitoring 의 메트릭 수집만 뽑아 재작성. 게임 로직은 최소한.
2. **IOCP 네트워크 코어만** — `NetServer`/세션 수명/패킷 풀/lock-free 자료구조만 현대화.
   DB·Redis·모니터링 제외.
3. **MMOFighter 전체 재작성** — 이동·공격·섹터 전파까지 포함한 동작하는 게임 서버로 복원.

### 스택

1. **Raw Win32 IOCP 유지 + 현대화** — IOCP 를 직접 다루되 `std::atomic`, RAII 소켓/핸들,
   operation 별 OVERLAPPED context, 명시적 state machine 으로 계약을 타입에 드러낸다.
   C++20 + CMake + vcpkg.
2. **C++20 코루틴 + Asio** — 크로스플랫폼 비동기로 재작성.
3. **Raw IOCP + 코루틴 어웨이터 자작** — IOCP 완료를 C++20 코루틴 awaiter 로 감싼다.

## 이유

- 범위 1번은 서버 개발의 핵심 축(네트워크·DB·성능·운영)을 한 저장소에서 전부 건드리면서도
  게임 로직 재현이라는 큰 비용을 피한다. 범위 2번은 DB/운영 커버가 비고, 3번은 과거에 지적된
  실패 패턴(범위 팽창)을 그대로 반복한다.
- 스택 1번을 버리지 않는 이유는 레거시 IOCP 를 **다시 배우는 것이 목적**이기 때문이다
  (문제 §1). Asio 로 바로 가면 저수준을 우회할 뿐 재학습이 일어나지 않고,
  Windows/VS/덤프 분석 경험도 드러나지 않는다.
- 스택 2번을 버리지 않는 이유는 **실무 스택 증명 자산이 지금 하나도 없기 때문**이다
  (문제 §2). 이것은 "나중에 필요할지도 모르는" 계획이 아니라 현재 결손이다.
- 그래서 셋은 **서로 대체재가 아니라 난도 단계**다. 같은 완료 조건(결함 재현 테스트·부하
  측정·CI)을 세 백엔드에 반복 적용하면, 백엔드 교체가 가능한 경계를 실제로 설계했다는
  증거가 나온다. 이것은 백엔드 하나로는 만들 수 없다.
- 증명 축 넷은 서로를 보강한다. 결함 재현 테스트가 없으면 "고쳤다" 가 주장에 그치고,
  CI 가 없으면 재현 가능성이 없고, 부하 측정이 없으면 백엔드 3종 비교가 불가능하고,
  덤프 분석이 없으면 운영 경험이 드러나지 않는다.

## 단점

- **가장 큰 위험은 이 결정 자체가 과거의 실패를 반복하는 것이다.** 이전 프로젝트들은
  "다음 마일스톤이 계속 생겨 종착점을 고정하지 못하는" 형태로 멈췄다. Phase 3 는 지금 호출자가 없는 계획이며, 정확히 그 실패의 형태를 하고 있다.
  Phase 2 는 실무 스택 결손이라는 현재 이유가 있지만, 그것이 Phase 1 을 미완으로 남길
  이유는 되지 못한다. Phase 게이트가 이것을 막는 유일한 장치다.
- Phase 1 만 남기고 중단해도 포트폴리오로 성립해야 한다. 성립하지 않는 설계는 잘못이다.
- raw Win32 IOCP 는 Windows 종속이라 Linux 서버 축은 덮지 못한다.
  Phase 2 의 Asio 가 그 축을 일부 덮지만, Phase 1 단계에서는 결손으로 남는다.
- 🔴 **소유자가 코드를 이해하고 소유해야 한다는 제약은 일정을 크게 늘린다.** AI 가 대신 짜면
  몇 배 빠르지만 그 결과물은 이 저장소에 넣을 수 없다. 이 비용은 결함이 아니라
  이 프로젝트가 사는 조건이다.
- 레거시 5종의 현재 빌드 가능 여부가 미확인이라(감사: v143 toolset 부재로 재빌드 실패),
  "결함을 재현한다" 는 계획이 레거시 빌드에 의존하면 시작부터 막힌다. 재현 방식은
  **결함마다 다르다** — 그대로 이식할 수 있는 것, fault injection 으로 바꿔야 하는 것,
  타입으로 차단하고 메커니즘만 보이는 것이 섞여 있다. 결함별 계약은
  `TASK-20260829-modern-iocp-phase1.md` 의 "결함 재현 계약" 표가 정본이다.
  일괄로 "패턴을 이식해 FAIL 을 본다" 고 말하면 D2·D3 에서 가짜 PASS 가 된다.

## 재검토 조건

- Phase 1 이 릴리즈되기 전에 Phase 2/3 코드를 만들고 싶어지면, 그 시점에 이 문서를 다시 연다.
- Phase 1 릴리즈 목표일까지 릴리즈되지 않으면 Phase 2/3 를 버리고 Phase 1 완결에만
  집중할지 다시 판정한다. 목표일은 로컬 기록에 둔다.
- 레거시 5종 중 하나라도 빌드 가능한 것이 확인되면, 재현 테스트를 레거시 실측으로 바꿀지
  재검토한다.
